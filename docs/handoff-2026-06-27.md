## Build / deploy / test — the current recipe (supersedes the F9 recipe in the old handoffs)

The harness flag is **not** baked into any preset; pass it explicitly.

```bash
# DEV build (harness compiled in):
cmake -S . -B out/build/macos-arm64 -G Xcode -DCMAKE_OSX_ARCHITECTURES=arm64 -DARCANUM_HARNESS=ON
cmake --build out/build/macos-arm64 --config Release --target arcanum-ce

# SHIP build (harness compiled out — what a release is):
cmake -S . -B out/build/macos-arm64-shipoff -G Xcode -DCMAKE_OSX_ARCHITECTURES=arm64 -DARCANUM_HARNESS=OFF
cmake --build out/build/macos-arm64-shipoff --config Release --target arcanum-ce
```
(`cmake --preset macos-arm64-release` builds a non-harness variant too.) **Always Release**
— Debug is 5-10× slower.

Deploy branch-named so it never clobbers the other side-by-side variants (shared `data/`,
`modules/`, `custom/` live at `~/Applications/Arcanum/`, beside the `.app`s):
```bash
rsync -a --delete "out/build/macos-arm64/Release/Arcanum Community Edition.app/Contents/" \
  "$HOME/Applications/Arcanum/Arcanum Community Edition (Perf GPU Accel).app/Contents/"
```

## Thread 1 — harness roadmap + make it a CI gate

`docs/arbiter-harness.md` is authoritative; priority order:

1. **`harness_settle()` — the highest-leverage capability.** `newgameat` survives the
   menu→game transition only because `sub_5412E0` pumps the loop until the spawn teleport
   completes. Promote that to a primitive (pump `teleport_ping`/load until
   `!teleport_is_teleporting()`) so in-game `tele`, map changes, and any mid-game transition
   keep the channel alive. This is exactly what blocked the clean cross-branch *town* workout
   on the old engines — they use idle-frame proxies today.
2. **Determinism.** A `seed <N>` command (fix the RNG) + premade char + fixed workout =
   byte-reproducible runs = real regression detection via `capture` pixel diffs.
3. **CI gate.** `bench-ab <toggle>` (same-launch, ambient-robust A/B of one option off→on)
   + `assert-render-under <ms>` (exit non-zero on regression). That turns the harness into a
   headless CI perf gate.
4. Named `scenario <name>` scripts under `tools/` (`town-stress`, `zoom-sweep`); `capture-diff`
   + auto-capture-on-spike; **headless software-only mode** (biggest force-multiplier, needs a
   GL-context-free SW render path).

- **Phase-2 extraction:** move the command channel + the new-game override fully into
  `harness.c` behind a few accessors (a render-path setter wrapping the `settings` static;
  the pregen-spawn entry is already public via `mainmenu_ui_harness_newgame_at`). Then all
  harness logic lives in one file.
- **Later — merge with the multiplayer arbiter:** one pump registering two command sets
  (perf/test here, MP-state there). Do it AFTER perf lands and MP rebases onto
  ui-improvements; don't collapse the two histories early.

## Thread 2 — finish the GPU render-path port

World + roofs + zoom + UI are on GPU. **What's left, and why it's gated:**

- **The GPU object pass / per-light palette lighting is the wall.** Objects (critters,
  scenery) are lit by a per-object *working palette*: each object's 256-entry palette is
  remapped by however many lights touch it — an arbitrary palette permutation. The GPU path
  expresses lighting as per-corner `COLOR_LERP` / per-texture `COLOR_CONST` tints over the
  *original* palette; it cannot reproduce an arbitrary 256-entry remap. So today:
  - Ambient-only / column-lit objects ARE on GPU (synthetic `COLOR_CONST` via
    `light_default_tint_for`).
  - Objects with per-object *local-light* palettes are **approximated**, not exact.
  - **Light splats** (`light.c:2448`) are the remaining unported item — blocked on the same wall.
- **The real fix** is to express per-object lighting in a GPU-expressible form:
  - (a) upload each object's working palette as a 256×1 LUT texture and do the palette
    indirection in a shader — needs a raw GL/Metal or custom SDL_Render path (SDL_Render
    can't sample a palette LUT); or
  - (b) bake the lit result CPU-side only when an object's light set *changes*, cache it as a
    GPU texture, and reuse it across static frames — trades VRAM + upload for the per-frame
    CPU lighting. **(b) is the smaller step**; score it against the vsync budget.
- **Metal native present** (`gpu_metal_vsync_present_suspect`): **keep forced-OpenGL for now.**
  GL does adaptive vsync via SDL (−28% sw-frame vs hard) and the 6-7 ms present is normal
  120 Hz vsync idle, not a defect. Metal *does* support native VRR
  (`presentAfterMinimumDuration` / `CAMetalDisplayLink` / ProMotion auto-VRR) — the SDL "not
  supported" is an SDL-2D-renderer limit, not Metal's. A Metal path is a real future option
  but needs (i) the Metal world pass fixed and (ii) native present-pacing plumbed past SDL.
  Bigger project; only if present-pacing becomes the bottleneck.
- **perception-fog rebase** (`perception_fog_rebase_trap`): if that branch comes back, it must
  re-home as a GPU present-time composite — it CPU-reads-back the framebuffer the GPU present
  path deleted, so a naive rebase renders invisible and wastes 8-17 ms/frame.
